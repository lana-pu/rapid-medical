# ADR-007 — Страница хранится списком блоков

**Статус:** принято · **Дата:** 2026-11-12 · Бриф: `docs/briefs/page-editor.md`

## Контекст
ADR-006: редактор добавляет, сдвигает и удаляет секции на странице. До этого решения страницы собирались из полей записей
при показе (`src/blocks/from-*.ts`), порядок секций был зашит в коде. Владелица 2026-11-12: делаем весь флоу редактора,
регионы пока остаются копиями (US, Europe, APAC — отдельные записи), наследование — позже.

## Решение
1. **Состав страницы — поле `blocks` (jsonb) записи.** Элемент: `{ id, type, variant, data, source? }`.
   - `solutions` (страницы терапий) и `pages` (текстовые страницы, лендинги) — колонка `blocks`.
   - Страницы-синглтоны (Home, About, Careers, Evidence ×3 региона, обзор терапий ×3) переезжают из `site_settings` в новую
     таблицу `site_pages` (`key` + `region`, `title`, `blocks`, `status`) и становятся ресурсом с workflow — у них
     появляются черновик, публикация и история, как у остальных страниц.
   - Поле `blocks` — обычное поле ресурса, поэтому `drafts`, `revisions`, Publish и restore работают без отдельного механизма (ADR-003).
2. **Данные блока хранятся в самом блоке.** Исключения подставляются при показе (`src/blocks/stored.ts → resolveBlocks`):
   - `source` — содержимое из коллекций (новости, публикации, команда, вебинары, карточки терапий, офисы, ссылки на версии
     в других регионах). Блок хранит только свои тексты (заголовок, вступление), список берётся из записей; правка элементов
     списка — в их записях.
   - Шаблоны в ссылках: `{region}` и `{product}` в `href` подставляются по странице.
3. **Перенос.** Старые адаптеры `from-*.ts` превращают поля записи в список блоков один раз: скрипт `scripts/migrate-blocks.ts`
   (идемпотентный, только записи с пустым `blocks`), вызывается из `scripts/bootstrap.ts` и после сида. Пока `blocks` пуст,
   страница собирается старым адаптером — сайт не ломается на незаполненной записи.
4. **Поля, переехавшие в блоки, уходят из форм админки** (тексты hero, benefits, overview, …, тела страниц, тексты синглтонов).
   В форме остаются служебные поля: slug, регион, продукт, группа в меню, SEO, статус — и ссылка «Edit on page».
   Колонки в БД пока не удаляются (откат возможен), код их больше не читает, кроме переноса.
5. **SEO и карточки** берут описание и картинку из первого hero-блока, если своих полей SEO нет.
6. **Правила структуры** — сервер (`src/admin/blocks-actions.ts`): тип и вариант из реестра, только разрешённые редактору
   пресеты, закреплённые блоки (`pinned`, регуляторика) нельзя удалить, сдвинуть или скопировать, они всегда в конце.
   Путь поля внутри блока проверяется по текущим данным: менять можно только строковые значения, структура
   (тип, вариант, id, массивы) правится только операциями над блоками.
7. **Одновременная правка.** Каждое сохранение передаёт версию страницы, которую видел редактор. Если с тех пор страницу
   поменял другой человек, сохранение отклоняется: «This page was changed by {имя} — reload to see their changes».

## Альтернативы
- **Хранить в блоках только порядок, данные оставить в полях записи.** Не даёт добавить вторую секцию того же типа и
  копировать секцию; поля записи и блоки пришлось бы синхронизировать вечно. Отклонено.
- **Одна таблица на все страницы.** Чище, но меняет URL-логику и маршруты сайта («миграция, а не переделка»). Отложено.
- **Синглтоны оставить в `site_settings`.** Нет истории версий и черновиков у ресурса; страница Home вела бы себя иначе, чем
  страница терапии. Отклонено.

## Последствия
- `src/blocks/from-*.ts` — источник переноса и запасной путь, не основной рендер.
- Наследование регионов (позже) ляжет на тот же список: блок получит признак «свой в регионе / общий».
- Колонки старых полей можно удалить отдельной миграцией после проверки на проде.
