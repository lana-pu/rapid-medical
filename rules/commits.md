# Commits — авто-коммит после каждого логического шага

## Принцип
Каждая завершённая фича, багфикс, законченная доработка или оформленный документ →
сразу commit, без отдельной команды и без вопроса «закоммитить?». Коммит — часть
выполнения шага.

## Правила

1. После завершённого шага: `git add <конкретные файлы шага>` + `git commit` с осмысленным
   сообщением — сразу.
2. Атомарность: одна фича / один фикс = один коммит. Разные изменения не смешивать.
3. НЕ `git add -A` / `git add .` вслепую — только файлы этого шага (не утащить `.env`,
   дампы, мусор, чужие параллельные правки).
4. Формат сообщения: `<проект> (<тип>): <описание>`
   - `проект` — короткое имя продукта (одно и то же во всех коммитах);
   - `тип` — `feat`, `fix`, `refactor`, `docs`, `chore`;
   - описание — что сделано, на языке проекта.
   Примеры: `myapp (feat): форма входа с валидацией email`,
   `myapp (fix): кнопка не активировалась при пустом поле`.
   Документация / спека / тесты — в ТОМ ЖЕ коммите, что и код.
5. Push зависит от автодеплоя:
   - push запускает автодеплой (push в `main` → прод) — перед каждым push спросить разрешение;
   - деплой отдельной командой (`./deploy.sh`) — push сразу после коммита;
   - shared-репозиторий — `git pull --rebase` перед push;
   - нет remote — только локальный коммит.
6. После push, закрывающего логический шаг, — `/save-session` (или эквивалент по
   `modules/ai-config/prompts/save-session.md`).
7. Если в репозитории уже принят другой формат сообщений (видно по `git log`) — следовать ему.
8. Перед коммитом: спека актуальна (изменение поведения → `docs/spec.md` / `docs/screens/*.md` в том же
   коммите; проект может форсить это pre-commit «спека-гейтом», обход для не-поведенческих правок —
   `SKIP_SPEC=1 git commit …`) и проект собирается (`npm run build` или `npx tsc --noEmit`). Упало —
   не коммитим: чиним причину.
9. Параллельные правки владелицы и других сессий — `rules/parallel-editing.md`.
10. Опасное (`git reset --hard`, `git push --force`, особенно в `main`) — только по явной просьбе.
