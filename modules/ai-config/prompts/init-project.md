# Init Project — старт проекта на базе библиотеки

Единственная точка входа в новый проект воркспейса. Запускать из корня воркспейса (папка с `modules/`)
или из уже созданной `projects/<slug>/`.

Что даёт пользователь: имя проекта (или AI берёт из первой фразы), одну фразу «что строишь» и, если есть,
ссылку на существующий git-репозиторий. Больше ничего руками не настраивает.

## 1. Папка и git
- Репозиторий уже есть → `git clone <url> projects/<slug>` (SSH по умолчанию). Режим **ретрофит**.
- Нет → `mkdir projects/<slug> && git init`, `.gitignore` (`node_modules`, `.env*`, `.next`, `dist`,
  `docs/memory/snapshots/`, `.claude/.cache/`). Режим **с нуля**.
- Проверь, что `projects/` в `.gitignore` корня воркспейса (у проекта свой git).

## 2. Подключить общий стек (локально, не в git проекта)
```bash
cd projects/<slug>
mkdir -p .claude
cp ../../.claude/project-settings.template.json .claude/settings.local.json   # общие хуки
ln -s ../../../.claude/skills .claude/skills                                   # общие скиллы
printf '%s\n' '.claude/settings.local.json' '.claude/skills' '.claude/.cache/' >> .git/info/exclude
```
Если у проекта уже есть `.claude/skills/` (свои скиллы) — не симлинкать папку целиком, а симлинкать
каждый общий скилл внутрь неё и добавить их в `.git/info/exclude`.

## 3. Скелет проекта
```
AGENTS.md            ← хаб проекта (CLAUDE.md → симлинк на него)
docs/spec.md         ← ## Продукт · ## Платформа · ## Данные · ## Доступы · ## Уведомления · ## Экраны (индекс)
docs/DESIGN.md       ← токены и правила визуала (пусто, если дизайна ещё нет — так и написать)
docs/screens/        ← спека на каждый экран
docs/rules/          ← правила ЭТОГО проекта (общие — в rules/ воркспейса, не копировать)
docs/memory/state.md         ← журнал «что произошло / что сейчас делаем»
docs/memory/BACKLOG.md       ← единственный список «что не сделано»: P0 → P1 → P2 → идеи → решения за владельцем
docs/memory/INDEX.md         ← реестр ADR, findings, sessions
docs/memory/infrastructure.md← где что развёрнуто, ENV (без значений), как деплоить
docs/memory/decisions/  findings/  sessions/
```
`AGENTS.md` проекта (< 4 KB): ссылка на `docs/spec.md → ## Продукт` вместо описания продукта; железные
правила проекта; таблица «Когда → Файл» (только существующие файлы); «Активная работа → state.md»;
«Бэклог → BACKLOG.md»; «История решений → INDEX.md». Если у проекта уже есть `AGENTS.md` с
автогенерируемыми блоками (например, `<!-- BEGIN:nextjs-agent-rules -->`) — сохранить их как есть.
`CLAUDE.md` → `ln -s AGENTS.md CLAUDE.md` (если `CLAUDE.md` уже есть со своим текстом — перенести текст
в `AGENTS.md`, потом симлинк).

## 4. Наполнение
**С нуля.** Спроси одной фразой «что делаешь?». По ответу сам определи направление и предложи план —
какие промты библиотеки и в каком порядке (обычно: `product/product-concept-interview` → спека экранов →
`design/*` дизайн-система и UI-кит → `development/*` → деплой → `seo-geo/*`). Нерелевантное пропусти
(внутренний сервис — без лендинга и SEO; контент-проект — без backend). После «да» — иди по плану.

**Ретрофит.** Код уже есть — методология догоняет код, код не трогаем:
1. Прочитай README, `package.json`, схему БД, роуты, git log. Ничего не запускай на прод.
2. `docs/spec.md` — восстанови по коду: продукт, роли, данные, доступы, индекс экранов (роуты).
   Чего нельзя понять из кода — в `BACKLOG.md → Решения за владельцем`, не выдумывать.
3. `docs/DESIGN.md` — опиши то, что реально есть (токены из CSS, примитивы). Нет дизайна — так и записать.
4. `docs/memory/infrastructure.md` — из Dockerfile / compose / vercel.json / CI / `.env.example`.
5. `docs/memory/decisions/ADR-001-…` — уже принятые решения стека (что выбрано и почему, если видно).
6. `BACKLOG.md` — из TODO в коде, «known issues» в README, незакрытых пунктов.
7. `state.md` — первая запись: «методология подключена, состояние кода на <sha>».
8. Push-политика в `docs/rules/commits.md` проекта: если push в main автоматически деплоит (Vercel,
   GitHub Actions на main) — пушить в main только проверенное и спрашивать перед push.
9. Покажи план следующих шагов по библиотеке исходя из того, что в проекте ещё не сделано.

## 5. Закрыть
Коммит в репозиторий проекта (`docs/`, `AGENTS.md`, `CLAUDE.md`) — атомарно, по `rules/commits.md`.
Push — по push-политике проекта. Затем `/save-session`.

Правила: не задавай вопросов, ответ на которые ясен из фразы, кода или библиотеки; веди только по
релевантным модулям; стек предлагай под задачу (в ретрофите — стек уже выбран, не менять).
