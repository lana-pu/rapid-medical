# Смоук сервиса — auth, валидации, сохранение на каждом экране, очистка

Запускай после подключения бэкенда (БД, auth, мутации) и после крупных изменений в формах/данных. Ловит баг «в интерфейсе сделал — а не сработало/не сохранилось»: мок чтения заменён, а мутация нет; забыт `await`; форма не шлёт запрос; ошибка молча проглочена; нет валидации.

Нужно на входе: запущенный сервис с БД и auth (URL dev/staging или прода); Playwright MCP (или другой способ управлять браузером); `docs/spec.md` с экранами и логикой.

## Главное правило
Проверяй результат **после жёсткой перезагрузки страницы или прямым запросом к БД**, а не по экрану сразу после сохранения. Оптимистичный UI показывает запись, даже если запись в базу провалилась.

Все создаваемые тестовые данные помечай маркером `__smoke__<6 случайных символов>` и удаляй в конце строго по нему — так проверка безопасна даже на базе с реальными данными.

## Шаги

### 1. Чек-лист по спеке
Пройди `docs/spec.md` (экраны, данные, автоматика, доступы), а также `docs/screens/*` и карту приложения, если есть. Выпиши:
- auth-флоу: регистрация, логин, выход, защита приватных страниц;
- по каждому экрану: действия (кнопки, формы, тоглы, смена статуса, привязки), что при каждом должно сохраниться/измениться в БД, переходы и состояния;
- правила валидации: обязательные поля, проверки формата, тексты ошибок по спеке.
Проверяем ровно логику из спеки, не абстрактный CRUD. Покажи чек-лист.

### 2. Аутентификация
- Регистрация нового аккаунта с маркером (напр. `__smoke__ab12cd@example.com`); если включено подтверждение email — пройди его.
- Выход и повторный логин — успешно.
- Вход с неверным паролем — отклоняется с понятной ошибкой.
- Приватная страница без логина — редирект/блок по спеке.
Любой провал — баг, почини.

### 3. Каждый экран по чек-листу (под __smoke__-пользователем)
Для каждой формы/действия:
- **a. Валидация**: отправь форму с пустым обязательным полем и с некорректным форматом (напр. email) — показывается ошибка из спеки, запись НЕ сохраняется.
- **b. Действие**: валидный сценарий в UI; в уникальное поле создаваемых записей — маркер.
- **c. Persist**: жёсткий reload (не SPA-переход) и проверка, что результат соответствует спеке и реально записан в БД, привязан к `userId` этого пользователя.
- **d.** Нет результата после перезагрузки или поведение расходится со спекой — баг. Ищи причину: мутация не подключена к БД; `onSubmit` не вызывает API; забыт `await`; ошибка проглочена в `try/catch`; неверный `userId` / RLS / валидация молча отклоняет.
- **e.** Полный жизненный цикл сущности: создать → прочитать → изменить → сменить статус/тогл (если есть) → удалить — каждый шаг с перезагрузкой и проверкой в БД.
- **f.** Отметь по экрану: валидация / create / read / update / delete — ✅ или ❌.
Расхождения «спека ↔ реальность» чини, пока экран не сойдётся со спекой.

### 4. Очистка
Удали все записи с маркером `__smoke__` и тестового пользователя с его данными — запросом к БД или через UI. Фильтруй строго по маркеру, чтобы не задеть seed и реальные данные. Покажи, что `__smoke__`-записей не осталось.

### 5. Отчёт
Таблица по экранам (auth / валидации / C-R-U-D / persist) + список экранов из спеки, которые не удалось проверить (пропуски покрытия — разобрать вручную). Любой ❌ — почини и прогони заново, пока всё не зелёное. Сохрани в `docs/audits/persistence-check-<YYYY-MM-DD>.md`.

## После проверки
Что именно должно сохраняться на каждом экране — закрепи в `docs/spec.md` и/или тест-кейсах проекта, чтобы это входило в регулярный UX/регресс-прогон.
