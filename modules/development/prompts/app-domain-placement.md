# Где живёт приложение — подстраница `/app` или поддомен `app.`

Запускай до SEO-индексации и PWA: от выбора зависят robots/sitemap и `start_url`/`scope` манифеста PWA.

Нужно на входе: задеплоенное приложение за nginx и `docs/memory/infrastructure.md` (домен, деплой, сертификаты).

## Два варианта

| | Подстраница `example.com/app` | Поддомен `app.example.com` |
|---|---|---|
| Что это | Лендинг и продукт в одном домене: `/` — лендинг, `/app` — продукт | Лендинг на основном домене, продукт на хосте `app.` |
| Когда брать | По умолчанию: один домен, ничего лишнего | Нужно чистое разделение «маркетинг ↔ продукт»: независимый деплой/масштаб, свой стек или команда, раздельные аналитика и логи |
| Что добавляет | Ничего сверх роутинга | DNS-запись, server-блок nginx с HTTPS, общие cookie сессии на `.<домен>` |
| PWA `start_url` | `/app` | `/` относительно поддомена |

**Нет явной причины разносить — подстраница.** Проверь, что `/` — лендинг, `/app` — продукт, залогиненного с `/` уводит в `/app`, гостя с `/app` — на вход (а запуск из установленного PWA, `display-mode: standalone`, сразу открывает `/app`). Зафиксируй в `docs/spec.md` (раздел «Домены»): «продукт на `/app`». Всё.

Выбран поддомен — промт ниже.

## Промт (вариант «поддомен»)

```
Помоги вынести приложение на поддомен app.<домен>, оставив лендинг на основном домене.
Стек — Next.js за nginx на VPS. Источник — docs/memory/infrastructure.md (деплой, домен,
сертификаты) и docs/spec.md. Чего не хватает (домен, IP, провайдер DNS) — спрашивай.

СНАЧАЛА СПРОСИ МЕНЯ:
1. Основной домен и где управляется DNS (регистратор, Cloudflare, хостер)?
2. Приложение и лендинг — один Next.js-проект или отдельные деплой-юниты (монорепо
   apps/app + apps/landing)?
3. Какая авторизация (Better Auth / NextAuth / своя) — нужны общие cookie на .<домен>.

ПОСЛЕ ОТВЕТОВ:

1. DNS. Запись для поддомена app:
   - A-запись app → IP основного домена (тот же сервер), либо
   - CNAME app → основной хост.
   Объясни, куда вписать в панели, и как проверить: `dig app.<домен>` / nslookup должны
   вернуть нужный IP. Распространение — до нескольких часов.

2. nginx — отдельный server-блок на app.<домен> + HTTPS:
   - проксирует app.<домен> на Next.js приложения (свой апстрим, если деплой отдельный);
   - сертификат: `certbot --nginx -d app.<домен>` (или wildcard *.<домен>) — только
     после того, как app.<домен> резолвится в IP сервера;
   - существующий блок основного домена не ломай — добавляй рядом.
   Покажи конфиг и команду перезагрузки nginx.

3. Куда переезжает продукт:
   - ОДИН проект: в middleware.ts разводи по хосту — app.<домен> → rewrite на роуты
     продукта, основной домен → лендинг и публичные страницы;
   - ОТДЕЛЬНЫЕ деплой-юниты: лендинг на example.com, приложение на app.example.com;
     поясни, что и где деплоится.

4. Общие cookie сессии на .<домен> (с ведущей точкой), чтобы вход на лендинге был виден
   на поддомене. Better Auth — advanced.crossSubDomainCookies / cookieDomain; другие —
   соответствующая опция.

5. Редиректы и ссылки:
   - CTA/signup на лендинге → https://app.<домен> (или app.<домен>/signup);
   - залогиненного на example.com/ → app.<домен>;
   - гостя на app.<домен> → страница входа.

6. PWA: manifest и service worker обслуживают app.<домен>; start_url и scope — от корня
   поддомена (/). Лендингу на основном домене PWA не нужен.

7. Зафиксируй: обнови docs/memory/infrastructure.md (поддомен, server-блок, сертификат),
   заведи ADR «subdomain» (почему вынесли, один проект или два), добавь строку в
   docs/memory/INDEX.md, отрази в docs/spec.md раздел «Домены».

ПОКАЖИ МНЕ:
- DNS-запись и проверку (`dig app.<домен>`);
- nginx-конфиг и что HTTPS выдаётся (`curl -I https://app.<домен>`);
- что вход на лендинге переносится на app (общая cookie работает);
- что осталось на основном домене, а что уехало на поддомен.
```

## Edge cases

- DNS не мгновенный — жди и проверяй `dig`; certbot только после резолва.
- Cookie без ведущей точки (`app.<домен>`) — лендинг её не видит, вход не переносится. Нужна `.<домен>`.
- Лендинг дёргает API приложения (`app.<домен>/api/...`) — это cross-origin, нужны CORS-заголовки. Проще держать API там же, где вызывающий фронт.
- Один проект на оба хоста через `middleware.ts` проще (один деплой, общая авторизация); два — когда лендинг реально отдельный (другой стек, команда, частота релизов).
- Поддомен можно добавить позже: `/app` остаётся рабочей базой.
