# Продуктовые email — письма по событиям продукта

Запускай, только если в `docs/spec.md` есть email-триггеры за рамками аккаунта: приглашение в команду/проект, подтверждение заказа/оплаты, смена статуса, ответ на комментарий/упоминание, дайджест. Нет таких — не нужен.

Нужно на входе: настроенная отправка писем — провайдер, подтверждённый домен (SPF/DKIM), `src/lib/email.ts`, общие компоненты `src/emails/` (см. `account-emails.md`). Переиспользуй их, провайдер заново не настраивай.

Это транзакционные письма, отправляемые напрямую при событии, — не канал in-app центра уведомлений.

## Объём и лимиты
Прикинь с пользователем ожидаемое число писем в день (триггеры × пользователи) и сверь с тарифом провайдера (у Resend бесплатно ~100/день, 3000/мес). Письмом шли только важное и редкое; частые и некритичные уведомления — в in-app центр (`account-settings-and-notifications.md`).

## Шаги
1. Выпиши из `docs/spec.md` все не-аккаунтные email-триггеры и покажи список — делаем только то, что есть в спеке.
2. На каждый триггер — TSX-шаблон в `src/emails/` по образцу существующих (тот же `Layout`/`Footer`/стили), с типизированными props (`name`, `orderId`, …).
3. Подключи к бизнес-событиям через функции из `src/lib/email.ts`:
   - отправка вызывается при событии (создан заказ, отправлен инвайт, сменился статус);
   - rate limit на отправку (защита от триггера в цикле);
   - идемпотентность: одно событие → одно письмо, повторный триггер дубль не шлёт (напр. по ключу события в БД).
4. Инвайты (если есть в спеке): письмо с одноразовой ссылкой-токеном с истечением; по ней приглашённый регистрируется/присоединяется; токен гасится после использования.
5. Зафиксируй ADR в `docs/memory/decisions/` (какие продуктовые письма, какие триггеры) и раздел «Email-уведомления» в `docs/spec.md`.

## Проверка
Вызови тестовое событие (создай заказ / отправь инвайт) — письмо приходит; повторный триггер второго письма не шлёт. Покажи одно отправленное письмо и результат проверки идемпотентности.
