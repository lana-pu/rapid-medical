# new-feature — разработка фичи: интервью → бриф → реализация ролями → ревью

Запускай, когда пользователь говорит «сделай фичу», «разработай», «добавь функцию», «новая функция», «реализуй», «давай обсудим перед реализацией». Работает в любом AI; в Claude Code оборачивается в скилл `/new-feature`.

Две части: **интервью** (поймать намерение и пробелы спеки, 2–6 вопросов) и **реализация** (исследование → архитектура → код → ревью).

## Шаг 0 — Способ реализации

| Возможности AI | Способ |
|---|---|
| Есть параллельные sub-агенты (Claude Code: `Agent`/`Task`) | Роли — параллельными агентами. Если доступен плагин `/feature-dev` — можно делегировать ему фазы реализации, передав готовый бриф. |
| Sub-агентов нет (Codex, Cursor и др.) | Роли последовательно в одном контексте, явно меняя «шляпу»: исследователь → архитектор → кодер → ревью логики → ревью безопасности → тех-лид. |

## PRD-first: без спецификации код не пишется

Источники правды: `docs/spec.md` (общая логика, модель данных), `docs/screens/<url>.md` (логика + `## Визуал` экрана), `docs/PRD.md` (продуктовый контекст).

| Что есть | Действие |
|---|---|
| Фича описана в `spec.md` / `screens/<url>.md` | интервью → бриф → реализация |
| Спека есть, фичи в ней нет | сначала допиши: общую логику — в `spec.md`, поведение и визуал экрана — в `docs/screens/<url>.md`; потом код |
| Спеки нет | предложи собрать спеку; минимум — что строим, для кого, зачем |

Меняешь экран — правишь `docs/screens/<url>.md` в том же коммите, что и код (это проверяет pre-commit спека-гейт, если настроен). Без спеки — только мелкие правки и багфиксы.

# Часть 1 — Интервью

**Не спрашивай** то, что можешь вывести сам: файлы, архитектуру в рамках стека, паттерны, риски, сложность, подход к тестам. Аудиторию, цель продукта и критерии успеха бери из `PRD.md`/`spec.md`.

**Спрашивай** то, что знает только пользователь и чего нет в спеке: что строим, что за рамками, поведение в крайних случаях.

**Новая технология** (БД, платёжка, очередь, авторизация, аналитика, Supabase/Firebase…) — не выбирай молча: предложи дефолт и спроси, подходит ли или есть своё требование. Фича вписывается в заданный стек — следуй ему без вопросов.

Протокол: перед интервью изучи проект (точки входа, похожие фичи, конвенции, модель данных) и прочитай `spec.md`, `screens/<url>.md`, `PRD.md`. Один вопрос за раз, где можно — 2–3 готовых варианта, пропускай то, на что уже ответили, разговорный тон, 2–6 вопросов.

Вопросы (адаптивно):
1. **Намерение** — что именно меняет фича. Есть в спеке → подтверди одной формулировкой.
2. **Аудитория и критерии успеха** — только если нет ни PRD, ни спеки.
3. **Крайние случаи** — пустой список, ошибка, нет доступа, очень длинные данные (главная польза интервью).
4. **Исключения** — что точно не включаем (если скоуп кажется широким).

Ещё 0–2 уточнения — только при двусмысленности или критической неизвестной. После 6 вопросов собирай бриф с тем, что есть.

### Бриф и одобрение

```markdown
# Бриф фичи: [название]

## Намерение
[что изменится, для кого, зачем]

## Аудитория
[кто пользуется]

## Критерии успеха
[наблюдаемые: «пользователь может X», «на экране видно Y», «при Z происходит …»]

## Исключения
[что НЕ строим]

## Контекст проекта
[стек, релевантные фичи, паттерны]

## Чеклист ревью
- [ ] [критерий 1]
- [ ] исключения соблюдены
```

Спроси: «Вот план. Всё верно — запускаю?» Код — только после одобрения. Бриф сохрани в `docs/briefs/<feature-name>.md` (не в корень).

# Часть 2 — Реализация

## Шаг 1 — Сложность

| Уровень | Триггеры | Роли |
|---|---|---|
| SIMPLE | 1–2 файла, без новых зависимостей и миграций | кодер + один ревьюер (логика + безопасность) |
| MEDIUM | 3–5 файлов, новые зависимости, API или БД | кодер + ревью логики + ревью безопасности + тех-лид |
| COMPLEX | 6+ файлов, несколько доменов, миграции, auth/платежи | то же + разбивка на части + анализ рисков до кода |

Фича трогает auth, платежи, персональные данные, миграции, новые внешние API, несколько модулей или может сломать тесты → минимум MEDIUM.

## Шаг 2 — План

Задачи: какие файлы, что делать, зависимости между задачами. MEDIUM/COMPLEX — сначала покажи план пользователю.

## Шаг 3 — Реализация ролями

1. **Исследователь** — 5–10 ключевых файлов: точки входа, похожие фичи, конвенции, откуда типы. Выпиши паттерны.
2. **Архитектор** — 2–3 варианта (минимальный / чистый / прагматичный), выбор с обоснованием.
3. **Кодер** — реализация по найденным конвенциям (для UI — цепочка `docs/DESIGN.md` → `src/shared/ui/` → экран, без хардкода).
4. **Ревью логики** — по чеклисту брифа: критерии успеха, исключения, edge cases.
5. **Ревью безопасности** — IDOR, авторизация, секреты, инъекции, XSS; сверка с правилами безопасности проекта (`development/prompts/security-check.md`).
6. **Тех-лид** (MEDIUM/COMPLEX) — не противоречит ли прошлым решениям (`docs/memory/decisions/`), нет ли дублирования.

Критичные замечания (🔴) применяй сразу, остальные предложи пользователю.

## Шаг 4 — Верификация

Запусти код / тесты / dev-сервер; убедись, что работает; для веба — пройди путь пользователя в браузере; тесты зелёные.

## Шаг 5 — Итог

```markdown
## Результат: [фича]
**Статус:** готово / частично / не завершено
**Сложность:** SIMPLE / MEDIUM / COMPLEX
### Выполнено
- [задача] — готово
### Файлы
- [файл] — что изменено
### Ревью
- логика / безопасность / архитектура — статус
### Нерешённые вопросы
```

После реализации обнови `docs/spec.md` и память проекта (`docs/memory/`), если она заведена.
