# Security-check: бэкенд-скоуп — auth/IDOR/сессии/инъекции + интеграции (AI, админка, REST API, боты, email, уведомления)

Запускай после подключения БД и auth, после добавления интеграций (AI, админка, REST API, Telegram, email, центр уведомлений) и перед релизом бэкенд-изменений. Это фокус-надстройка над общим аудитом: какие векторы проверить особенно и какие тесты прогнать.

Нужно на входе: общий аудит безопасности — скилл `/security-check` или промт `security-check.md` из модуля development.

## Как запускать
1. Прочитай растущий чек-лист проекта `docs/security-checklist.md` (нет — создай) и сверься с ним.
2. Запусти общий аудит (`/security-check` или «прочитай `security-check.md` и выполни») с контекстом: «бэкенд: БД + auth + интеграции, фокус — разделы ниже».
3. Проверяй только векторы, которые реально есть в проекте; отсутствующие отметь в отчёте как «не применимо».
4. Отчёт — `docs/audits/security-check-<YYYY-MM-DD>.md`. В конце допиши в `docs/security-checklist.md` новые векторы этого прогона — чек-лист копится.

## Критично: БД и auth

- **Authorization & IDOR.** Каждый API-роут проверяет сессию; на ресурсах с владельцем — `entity.userId === session.user.id` (или явное право роли admin). На чужой ресурс — 404.
- **Authentication / Sessions.** Хеш паролей (bcrypt ≥ 12 раундов / scrypt / argon2); сессии в БД с `expiresAt`; cookie `HttpOnly` + `Secure` + `SameSite=Lax`; rate limit на `/api/auth/*`; защита от user-enumeration (одинаковые ответы на логине и «забыли пароль»).
- **Inputs & Injection.** Только параметризованные запросы ORM (raw SQL — через tagged template, не сборкой строк); нет mass assignment — явный destructure / `z.pick`, никаких `db.update({ data: req.body })`.
- **CSRF.** `SameSite=Lax` + проверка `Origin` на state-changing API; встроенная защита auth-библиотеки не выключена.
- **Secrets & Deployment.** `.env.production` содержит актуальные `DATABASE_URL` и секрет auth; секрет auth ≥ 32 байт, не дефолтный и НЕ совпадает с dev; порт БД (5432) закрыт снаружи (UFW / bind на 127.0.0.1).
- **Регрессия:** HTTP security headers; SSH/UFW/fail2ban не сломаны.

### Обязательный IDOR-тест
Создай два тестовых аккаунта A и B, каждым — по ресурсу. Под A: открыть `/<resource>/<id-B>` по URL и `DELETE /api/<resource>/<id-B>` через curl с кукой A → 404 в обоих случаях. Затем наоборот. Прошло — отметь в отчёте «IDOR проверен на двух аккаунтах, не пробивается». Тестовые аккаунты после проверки удали.

## Интеграции (если есть в проекте)

### AI в продукте
- [ ] Ключ провайдера (`OPENROUTER_API_KEY` / `ANTHROPIC_API_KEY` / …) только в серверном env, не во frontend-бандле.
- [ ] Все AI-вызовы — через бэкенд, не из браузера.
- [ ] Rate limit на `/api/ai/*` (напр. 10 req/min на пользователя) и лимит расхода на пользователя.
- [ ] Защита от prompt injection: пользовательский ввод отделён от системных инструкций (отдельное сообщение/разделители), не исполняется как инструкция; у AI нет доступа к действиям/данным сверх прав пользователя.
- [ ] Логирование AI-запросов для аудита (без лишних персональных данных).

### Админка
- [ ] `/admin/*` и каждый admin-endpoint проверяют роль на сервере.
- [ ] Все admin-мутации пишутся в журнал действий.
- [ ] Список админов минимален; админ не может удалить/разжаловать сам себя.

### REST API наружу
- [ ] API-ключи хранятся как хеш, не plaintext; показываются один раз.
- [ ] Scope-авторизация (read/write по типам ресурсов); данные фильтруются по владельцу ключа.
- [ ] Rate limit на ключ (напр. 100/мин) с `429` + `Retry-After`.
- [ ] Логирование вызовов; отзыв ключа работает сразу.
- [ ] Только HTTPS; документация может быть публичной, ключи — нет.

### Telegram-оповещения владельцу
- [ ] Токен бота только в env, не в коде/репозитории (`chat_id` — не секрет).
- [ ] Отправка строго по белому списку `chat_id`; бот не отвечает всем, кто ему написал.
- [ ] Только исходящие: нет webhook, команд, привязки аккаунтов.
- [ ] В тексте алертов нет паролей, токенов, персональных данных.

### Email
- [ ] Ключи провайдера / SMTP в env.
- [ ] Rate limit отправок (напр. 5/час на пользователя) и идемпотентность событийных писем.
- [ ] Подтверждение email перед важными уведомлениями.
- [ ] Отписка в маркетинговых письмах.
- [ ] SPF + DKIM + DMARC настроены для домена.

### In-app уведомления
- [ ] Уведомления изолированы по `userId` (нельзя прочитать/отметить чужие).
- [ ] Real-time каналы (SSE/WebSocket) аутентифицированы; подписка только на свои уведомления.

### Файлы
- [ ] Отдача приватных файлов — с проверкой владельца / signed URLs; whitelist типов, лимит размера, ключ — UUID.

## После аудита
1. Покажи найденное: 🔴 (критично) и ⚠️ (важно).
2. 🔴 — план починки и сразу чини; после починки — повторный прогон, пока 🔴 нет.
3. ⚠️ — в бэклог проекта (`docs/memory/BACKLOG.md` или `docs/security-todo.md`).
4. Важные решения (политика паролей, отказ от OAuth, базовая линия безопасности) — ADR в `docs/memory/decisions/`.
5. Устойчивый IDOR-тест закрепи в тест-кейсах проекта как регрессионный сценарий.
