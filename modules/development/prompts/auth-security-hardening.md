# Защита auth — хеширование, cookie, rate limit, user-enumeration, CSRF

Запускай сразу после настройки auth и при изменениях в auth-флоу. Результат: базовый набор защит включён, типовые атаки на формы (перебор пароля, перехват cookie, прощупывание email) не проходят; в проекте есть чек-лист `docs/rules/auth-security.md`.

Нужно на входе: работающий auth (`auth-setup.md`).

Примеры — для better-auth + Next.js middleware; другая библиотека — проверь эквивалентные настройки.

## Проверь и настрой

1. **Хеширование паролей.** Библиотека хеширует scrypt/bcrypt/argon2 — проверь в конфиге auth. В БД только хеш, никакой колонки с паролем в открытом виде (проверь таблицы через Prisma Studio / SQL).

2. **Cookie сессии**: `HttpOnly: true`, `Secure: true` на проде (на localhost — false), `SameSite: 'lax'`, `Path: '/'`. Проверь в DevTools → Application → Cookies после логина.

3. **Rate limiting.** В middleware на `/api/auth/*` — лимит (напр. 5/мин на IP); если нет — добавь. Дополнительно — регистрация 3/час на IP:
   ```ts
   if (path.startsWith('/api/auth/sign-up')) {
     if (!rateLimit(`signup:${ip}`, 3, 60 * 60 * 1000)) {
       return new NextResponse('Too many signups', { status: 429 })
     }
   }
   ```
   In-memory rate limit работает только для одного инстанса; при нескольких — Redis/Upstash.

4. **Защита от user-enumeration** (узнать, есть ли email в системе):
   - логин: одно сообщение для неверного email и неверного пароля — «Неверный email или пароль»;
   - время ответа примерно одинаковое (библиотека должна делать фиктивный хеш для несуществующего email — проверь);
   - «Забыли пароль»: ответ одинаковый, есть email или нет;
   - регистрация с уже существующим email — спроси пользователя, какой вариант:
     - **A (безопасность)**: всегда «успех», запись не создаётся, на адрес уходит письмо «на вашу почту пытались зарегистрироваться — если это не вы, игнорируйте»;
     - **B (UX)**: generic-ошибка без «email уже занят».
     По умолчанию B.

5. **CSRF.** Встроенная защита auth-библиотеки (state/Origin-проверка) включена — не выключай. На state-changing API — `SameSite=Lax` + проверка `Origin`.

6. **Пароль.** Минимум 8 символов (`minPasswordLength`). Проверку по утечкам (haveibeenpwned, k-anonymity) и оценку силы (zxcvbn) — по желанию, по умолчанию не включаем.

## Тестовый прогон
1. 6 неудачных попыток входа подряд → последняя `429`.
2. Регистрация с существующим email → поведение по выбранному варианту A/B.
3. Кука после логина: `HttpOnly`, `Secure` (прод), `SameSite=Lax`.
4. `curl` к защищённому `/api/<protected>` без сессии → `401`.
5. SQL-инъекция в email при логине (`admin@test.com' OR '1'='1`) → обычная ошибка (ORM параметризует запросы).

## Чек-лист для будущих фич
Создай `docs/rules/auth-security.md` и добавь строку-триггер на него в `AGENTS.md` проекта:

```markdown
# Auth Security — что проверять при добавлении auth-фич

- Все /api/auth/* проходят через rate limiting
- Логин — единое сообщение для неверного email/пароля; «забыли пароль» — одинаковый ответ
- Регистрация — реализован выбранный вариант (A/B) защиты от user-enumeration
- Cookie: HttpOnly + Secure (prod) + SameSite=Lax
- CSRF: встроенная защита auth-библиотеки не выключена
- Пароль: минимум 8 символов, всегда хешируется (bcrypt/scrypt/argon2)
- IDOR: каждая операция над ресурсом пользователя проверяет userId
```

Выбранный вариант A/B и настройки rate limit зафиксируй в `docs/spec.md` (раздел auth/доступы).

В конце покажи содержимое `docs/rules/auth-security.md` и результаты пяти тестов.

## Нюансы
- Нет HTTPS на проде → `Secure`-cookie не выставится; URL auth в env должен начинаться с `https://`.
- На `localhost` cookie ведут себя по-разному в разных браузерах — финальная проверка на проде.
