# Спеки экранов `docs/screens/` — создание и сверка с кодом

Запускай, чтобы на каждый ключевой экран был полный spec (состояния, элементы, сообщения, валидация), и при сверке спек с кодом. Существующие файлы не пересоздавать — проверять и дополнять.

Нужно на входе: приложение с экранами; `docs/PRD.md` / `docs/spec.md` (главный сценарий).

## Промт

```
Проверь и доведи до полноты docs/screens/. Файл экрана уже есть (например, с разделом
«## Визуал») — НЕ пересоздавай: допиши недостающее. Файла нет — создай. Сверь каждый
с кодом: расходится — чини одну сторону (спека = источник правды).

Минимум — экраны:
- docs/screens/auth.md (логин + регистрация)
- docs/screens/dashboard.md
- docs/screens/<основной-флоу>.md (главный сценарий из PRD)
- docs/screens/settings.md

Делай ПО ОДНОМУ экрану, с моим подтверждением после каждого.

ФОРМАТ docs/screens/<screen>.md (строго):

# Экран: <Название>

**URL:** `/path`
**Доступ:** роль = ... | все авторизованные | гость

---

## Состояния экрана

| Состояние | Условие |
|---|---|
| Загрузка | данные ещё не получены |
| Пустой | список пуст |
| Заполненный | есть ≥ 1 запись |
| Ошибка | запрос к API вернул ошибку |

## Элементы интерфейса

### <Название элемента, например "Кнопка Создать">

- **Видим:** условие = значение ИЛИ другое условие
- **Скрыт:** роль ≠ администратор
- **Активен:** статус ≠ завершён
- **Неактивен:** статус = завершён ИЛИ нет прав
- **При действии:** куда ведёт, какой запрос, какое сообщение

(Символы: =, ≠, >, <, ≥, ≤, ИЛИ, И, НЕ, ∈, ∉)

## Сообщения

| Ситуация | Тип | Текст сообщения |
|---|---|---|
| Успешное сохранение | success | «Изменения сохранены» |
| Нет прав | error | «Недостаточно прав для этого действия» |
| Поле не заполнено | error | «Заполните поле <название>» |
| Сеть недоступна | error | «Нет соединения. Попробуйте позже» |

## Автоматика и уведомления

| Триггер | Канал | Получатель | Текст / Действие |
|---|---|---|---|

(Пусто, пока у экрана нет уведомлений.)

## Валидация полей

| Поле | Правило | Сообщение об ошибке |
|---|---|---|
| Email | формат email, уникальный | «Введите корректный email» |
| Пароль | ≥ 8 символов | «Минимум 8 символов» |
| Название | не пустое, ≤ 100 символов | «Введите название» |

---

ИСТОЧНИК — реальный код страницы (в FSD: src/pages/<page>/ или src/app/.../page.tsx
и используемые widgets/features). Видишь компоненты — описываешь поведение.
Неочевидное поведение (сложное условие скрытия) — спроси меня одной строкой.

Spec описывает НАМЕРЕНИЕ, а не текущий код. Если в коде кнопка всегда показана, а
логически должна скрываться у гостя — пиши правильное поведение; расхождение
поймают тест-кейсы (development/prompts/test-cases.md).

После каждого spec: покажи → жди подтверждения/правок → следующий.

ПОКАЖИ МНЕ финальный docs/screens/dashboard.md как пример законченной спеки.
```

## Edge cases

- Экран с режимами (например, табы /settings: Профиль / Безопасность / Уведомления) — раздел на вкладку или отдельный spec, по объёму.
- 15+ элементов — разбить на разделы по функциональным группам.
- Сообщения — именно тексты: «Успех» — плохо, «Изменения сохранены» — хорошо.
