# BDD тест-кейсы на критичные пути + автотесты и тест-гейт

Запускай, когда в сервисе есть auth и главный флоу: сначала текстовые сценарии и ручной прогон, затем (когда сценарии устоялись) — автоматизация и гейт на push и деплой.

Нужно на входе: работающий сервис; `docs/PRD.md` / `docs/spec.md`, `docs/screens/*.md`. Для автотестов — git; для гейта в деплое — `deploy.sh`.

Формат: **Дано / Когда / Тогда** (Given / When / Then), black-box — поведение через UI / API, не через внутренние функции.

## Часть 1 — сценарии и ручной прогон

```
Создай docs/test-cases.md с 3-5 сценариями на критичные пути сервиса.

ФОРМАТ КАЖДОГО СЦЕНАРИЯ:

## Сценарий N: <Название>

- **Дано:** <предусловие>
- **Когда:** <действие пользователя>
- **Тогда:** <ожидаемый результат 1>
- **Тогда:** <ожидаемый результат 2>
- **Тогда:** <side effect — email, audit log, redirect и т.д.>

ОБЯЗАТЕЛЬНЫЙ МИНИМУМ:

## Сценарий 1: Регистрация и первый вход
- **Дано:** пользователь не зарегистрирован
- **Когда:** заполняет форму регистрации с валидным email и паролем ≥ 8 символов
- **Тогда:** создаётся User в БД с hashedPassword (не plaintext)
- **Тогда:** редирект на /dashboard
- **Тогда:** cookie сессии: HttpOnly + Secure (на проде) + SameSite=Lax
- **Тогда:** в Header виден avatar / имя пользователя

## Сценарий 2: Логин с неверным паролем — единый ответ
- **Дано:** пользователь зарегистрирован
- **Когда:** входит с неверным паролем
- **Тогда:** ошибка «Неверный email или пароль» — такая же для несуществующего email
  (защита от user-enumeration)
- **Тогда:** время ответа примерно одинаковое в обоих случаях
- **Тогда:** после 5 неудачных попыток с одного IP — 429 Too many requests (rate limit
  на /api/auth/*)

## Сценарий 3: IDOR закрыт
- **Дано:** два авторизованных пользователя A и B, у каждого свой <ресурс>
- **Когда:** A открывает /<ресурс>/<id-B> по URL
- **Тогда:** 404 (не данные B и не «Forbidden» — это утечка информации)
- **Когда:** A делает DELETE /api/<ресурс>/<id-B>
- **Тогда:** 404 / 403, ресурс B остаётся в БД

## Сценарий 4: Защита роутов
- **Дано:** пользователь не авторизован
- **Когда:** открывает /dashboard по URL
- **Тогда:** редирект на /login
- **Когда:** успешно логинится
- **Тогда:** редирект на /dashboard (не на главную и не на /login)

## Сценарий 5: <Главный флоу продукта по PRD>
- **Дано:** пользователь залогинен, на /dashboard
- **Когда:** нажимает «Создать», заполняет форму, отправляет
- **Тогда:** запись создана в БД с правильным userId
- **Тогда:** в списке новая запись с ожидаемыми полями
- **Тогда:** toast из спеки экрана
- **Тогда:** после перезагрузки запись видна
(Адаптируй под продукт: e-commerce — «корзина и заказ», трекер привычек — «отметить
выполнение».)

## Сценарий 6 (опц.): Постоянная обвязка и быстрая навигация
- **Дано:** залогиненный пользователь на внутреннем экране с меню/шапкой
- **Когда:** переключается между 2-3 разделами через меню (<Link>)
- **Тогда:** меню/шапка не мигают — меняется только контент (обвязка в (app)/layout.tsx)
- **Тогда:** в DevTools → Network нет нового запроса document (мягкая навигация)
- **Тогда:** активный пункт меню подсвечен по текущему URL
(Ловит регрессию: меню внутри страницы или <a href> вместо <Link>.)

BLACK-BOX:
❌ «функция createTask должна вызвать prisma.task.create» — white-box, привязан к коду
✅ «после клика «Создать» в БД появилась запись и она видна на /dashboard»

РУЧНОЙ ПРОГОН: пройди каждый сценарий в браузере и отметь в файле:
- ✅ прошёл; 🟡 частично (отличается, но не критично); 🔴 сломано.
🟡/🔴 — код расходится со спекой: обсуди со мной, что правильно (spec или код), и поправь.

ПОКАЖИ МНЕ:
- docs/test-cases.md;
- результаты ✅/🟡/🔴 по каждому;
- что починили по 🟡/🔴.
```

## Часть 2 — автотесты и тест-гейт

Два слоя: **e2e (Playwright)** — главные пользовательские пути через браузер, один тест ≈ один сценарий; **интеграционные (Vitest + supertest / route handlers)** — API и серверная логика без браузера: IDOR, user-enumeration, rate limit, валидация.

```
Автоматизируй BDD-сценарии из docs/test-cases.md. Стек — Next.js (App Router),
Playwright для e2e, Vitest для интеграционных. Источник истины — test-cases.md
(каждый автотест соответствует сценарию по номеру и названию).

1. Поставь и настрой Playwright (`npm init playwright@latest`) и Vitest в приложении
   сервиса (в монорепо — development/apps/app/). Тестовая БД отдельная (НЕ боевая):
   своя база или schema, миграции на ней, очистка между тестами.

2. e2e (e2e/*.spec.ts) — регистрация и вход, защита роутов (гость на /app → /login),
   главный флоу. Проверяй видимый результат И побочные эффекты (запись в БД, redirect,
   cookie HttpOnly).

3. Интеграционные (tests/*.test.ts) — IDOR (A → ресурс B → 404, ресурс B цел),
   user-enumeration (единый ответ), rate limit (429 после лимита на /api/auth/*),
   серверная валидация полей.

4. Скрипты в package.json: `test` (Vitest), `test:e2e` (Playwright), `test:all`.
   Детерминированные данные (фабрики / seed тестовой базы), не Math.random().

5. ГЕЙТ В ДВУХ ТОЧКАХ:
   - pre-push хук (или CI, например GitHub Actions): `test:all` перед push/мержем,
     красные тесты блокируют отправку;
   - deploy.sh: `test:all` перед переключением трафика, красные тесты останавливают
     выкат;
   - свяжи с существующими гейтами проекта (спека-гейт, security-precheck) — не
     дублируй, добавь запуск тестов рядом.

6. Зафиксируй: ADR «test-automation» (что покрыли, чем), раздел «Тесты» в docs/spec.md
   и AGENTS.md (как запускать, где тестовая БД), строка в docs/memory/INDEX.md.

ПОКАЖИ МНЕ:
- зелёный `test:all` локально;
- что красный тест блокирует push И останавливает deploy.sh (на заведомо ломающей
  правке);
- какие сценарии покрыты e2e, какие — интеграцией, и почему.
```

Маленький проект без пользователей — минимум e2e на 2–3 главных пути + интеграционный тест на IDOR/auth, но в гейте.

## Правило: тест туда, где был баг

AI пишет фикс и ревьюит его с теми же допущениями, поэтому повторяет ошибку. Не гнаться за 100% покрытием — писать тест ровно на найденный и исправленный баг. Покрытие растёт по следам реальных багов.

- **Sandbox vs prod.** Если есть mock/sandbox-режим (демо без БД), при добавлении поля в ответ API — тест на **форму ответа** (все обязательные поля) в боевом И sandbox-режиме. Sandbox-тесты без БД, быстрые.
- Называй тест по багу: `// BUG-R1: notification_settings терялось в sandbox`.

## Edge cases

- Главный флоу длинный — разбей на 2–3 сценария с одним фокусом.
- Нет auth (публичный сервис) — сценарии 1–4 неприменимы, замени сценариями главного флоу.
- Ресурс публичный по ссылке (share by link) — IDOR-сценарий проверяет токен, не userId.
