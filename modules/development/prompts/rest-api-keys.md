# REST API наружу + API-ключи

Запускай, когда данные продукта нужно отдавать вне приложения: интеграции и автоматизация (Zapier / Make / n8n), выгрузки в таблицы/BI, мобильное приложение или второй фронтенд, внешние сервисы по расписанию. Нечего отдавать наружу (нет в `docs/spec.md`) — не нужен.

Внешний клиент не имеет сессии-куки, поэтому авторизуется API-ключом: ключ выдаётся конкретной интеграции, определяет «кто стучится» и «что разрешено» (scopes) и отзывается отдельно от остальных.

Нужно на входе: auth и БД; место для выдачи/отзыва ключей — админка (`admin-panel.md`) или страница настроек пользователя.

Стек по умолчанию: Next.js App Router + Prisma. Другой стек — адаптируй.

## 0. Сначала разбор, потом код
Разбери с пользователем: какие интеграции из спеки реально нужны, что им читать/писать, нужны ли они вообще. Есть скилл `/new-feature` — используй его; нет — задай уточняющие вопросы, покажи план, реализуй после согласования.

## 1. Модель ключа
```prisma
model ApiKey {
  id        String    @id @default(uuid())
  userId    String              // чей ключ
  keyHash   String    @unique   // в БД — ХЕШ ключа, не сам ключ
  name      String              // назначение: "Zapier", "Мобилка", "Экспорт в BI"
  scopes    String[]            // ['read:orders', 'write:posts']
  lastUsed  DateTime?
  expiresAt DateTime?
  revokedAt DateTime?
  createdAt DateTime  @default(now())
  @@index([userId])
}
```
Ключ генерируется криптостойко и показывается пользователю **один раз** при создании; дальше хранится только хеш (напр. SHA-256). Выдача/отзыв — из админки или настроек, каждое действие в журнал (`apikey.create` / `apikey.revoke`).

## 2. Endpoints `/api/v1/*`
```
GET    /api/v1/<entity>        — список (пагинация)
GET    /api/v1/<entity>/:id    — один
POST   /api/v1/<entity>        — создать
PATCH  /api/v1/<entity>/:id    — обновить
DELETE /api/v1/<entity>/:id    — удалить
```
Версия в пути — чтобы менять API, не ломая старые интеграции. Входные данные валидируй схемой (напр. zod), без mass assignment.

## 3. Аутентификация по ключу
Обработчик на `/api/v1/*`: читает `Authorization: Bearer <key>`, хеширует, ищет в `ApiKey` (не отозван, не истёк), проверяет scope под операцию (запись/удаление требуют `write:`), обновляет `lastUsed`. Нет ключа / истёк / отозван → `401`; не тот scope → `403`. Данные фильтруются по владельцу ключа (`userId`) — ключ не видит чужое.

## 4. Rate limit (строже, чем для людей)
На ключ: напр. 100 req/min и 1000 req/day (под свой случай). Превышение → `429` + `Retry-After`.

## 5. Документация — `docs/api.md`
Для каждого endpoint: метод, путь, нужный scope, параметры, пример `curl`, формат ответа.

```markdown
## GET /api/v1/orders
Список заказов. Авторизация: Bearer-ключ со scope `read:orders`.
Параметры: page (1), limit (20, max 100), status (опц.).
Ответ: { "data": [...], "pagination": { "page": 1, "total": 150 } }
```

## 6. Пример сценария (по желанию — 1–2 под случай пользователя)
- **n8n self-hosted**: контейнер рядом с приложением (`docker run -d --name n8n -p 127.0.0.1:5678:5678 -v n8n_data:/home/node/.n8n n8nio/n8n` или сервис в docker-compose за nginx с паролем); нода HTTP Request с `Authorization: Bearer <ключ>` → `GET /api/v1/<entity>` → дальше Telegram / Google Sheets / задача.
- **Zapier / Make**: триггер по расписанию → HTTP-запрос с ключом → действие в другом сервисе.
- **Выгрузка в таблицу/BI**: скрипт / Apps Script по ключу тянет `GET /api/v1/<entity>?limit=100`.
- **Исходящий вебхук** (если внешнему сервису нужно узнавать о событиях сразу): при событии вы шлёте POST на его URL (с подписью HMAC) — это отдельный механизм, не ключ к вашему API.
Покажи полный путь на одном примере: выдал ключ → настроил интеграцию (или curl) → данные пришли → отозвал ключ → доступ пропал.

## После реализации
1. Выдай тестовый ключ, покажи `curl -H "Authorization: Bearer <key>" https://<domain>/api/v1/<entity>`.
2. Покажи: без ключа / с чужим scope — `401`/`403`; превышение лимита — `429`.
3. Отзови ключ → тот же запрос перестаёт работать.
4. `docs/spec.md` — раздел «API»; ADR в `docs/memory/decisions/` (зачем REST, какие scopes, лимиты).
