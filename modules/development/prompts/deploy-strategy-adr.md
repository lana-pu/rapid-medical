# Стратегия деплоя — выбор и ADR

Запускай перед первой выкладкой проекта или при смене способа деплоя.

Нужно на входе: `docs/spec.md` (тип проекта: статика / сервер / БД / файлы / фоновые задачи).

Результат: ADR `docs/memory/decisions/ADR-<NNN>-deploy-strategy.md` (следующий свободный номер) с выбранной стратегией; строка в `docs/memory/INDEX.md`.

## Шаг 1 — Покажи варианты и компромиссы (кратко, таблицей)

| Подход | Как | Плюсы | Минусы |
|---|---|---|---|
| Ручной через AI/SSH | «задеплой» → AI по SSH запускает `deploy.sh`, проверяет логи и URL | прозрачно, легко дебажить | не происходит сам после push |
| Git-based на VPS | push → на сервере `git pull` + перезапуск | версия = коммит, понятный откат | серверу нужен доступ к репо |
| CI/CD | push в main → сборка/тесты → деплой | стандарт для команды | секреты в CI, сложнее дебажить, один push может сломать прод |
| Платформа (Vercel / Netlify / Render / Railway) | push → платформа билдит и деплоит | быстрый старт, мало DevOps | ограничения по backend, БД, файлам, фоновым задачам, региону, цене |
| scp / rsync артефактов | копирование готовых файлов | просто для статики | слабая повторяемость и откат |

Две развилки:
- **Когда запускается:** автоматически на push в `main` (прод всегда = main, но случайный push сразу в проде) или по команде «задеплой» (контроль момента, нужна дисциплина).
- **Где собирается Docker-образ:** на сервере (`docker compose up -d --build`) — просто, но `next build` прожорлив, а dockerd после сборки не возвращает память ОС → на VPS ~1 ГБ swap и TTFB в секунды; или в CI/локально → push в реестр (GHCR) → на сервере `docker compose pull && up -d` — VPS не собирает, памяти хватает, перезапуск демона не нужен (важно для zero-downtime). Рекомендация: на боксе ≤ 1–2 ГБ собирать **не** на сервере. Если пока собираем на сервере — обязательна пост-деплой гигиена (`docker builder prune -f`, перезапуск распухшего dockerd, swap + `vm.swappiness=10`) из `development/prompts/vps-docker-compose.md`.

## Шаг 2 — Спроси выбор

Ручной через AI/SSH / git-based на VPS / CI/CD / платформа / другое. Не знает → дефолт: **VPS + docker-compose + `deploy.sh`, запуск вручную через AI/SSH; внутри `deploy.sh` — `git pull`, если код обновляется через GitHub.**

Уже есть рабочий деплой на платформе → не ломать: зафиксировать текущую стратегию, риски и условия переезда. Нет VPS → VPS-часть отложить, ADR со `Status: Deferred` и причиной. Простой публичный проект без БД, файлов и server-side задач → платформа может быть лучше VPS.

## Шаг 3 — ADR

```markdown
# ADR-<NNN>: Стратегия деплоя

## Context
Нужен понятный, повторяемый и безопасный способ выкладывать <продукт> в публичный доступ.
Тип проекта: <статика / приложение с сервером / БД / файлы / интеграции>.

## Decision
Выбрано: <вариант>.
- Где собирается образ: <на сервере / CI → GHCR → pull>.
- Запуск: <по команде «задеплой» / авто на push в main>.
- Единая точка деплоя: <deploy.sh на сервере / платформа>.

## Alternatives Considered
- Ручной через AI/SSH — прозрачно; нет авто-деплоя.
- Git-based на VPS — версия = коммит; нужен доступ сервера к репо.
- CI/CD — стандарт для команды; секреты в CI, риск сломать прод одним push.
- Платформы — быстрый старт; ограничения backend/БД/файлов/цены.
- scp/rsync — просто для статики; слабая повторяемость и откат.

## Consequences
- Команды «задеплой», «откати», «покажи логи» опираются на этот ADR (`development/prompts/deploy-cheatsheet.md`).
- После настройки стратегия описывается в `docs/memory/infrastructure.md`.
- Смена стратегии → новый ADR или обновление этого с причиной.
- Размер VPS: 1 ГБ / 1 vCPU хватает приложению (Next ~150–300 МБ + Postgres с `mem_limit` и swappiness=10); узко на сборке образа на сервере, росте трафика, больших миграциях, активном файловом хранилище. Пора на 2 ГБ+: постоянный swap (`vmstat` si/so > 0 не только на деплое), OOM-kill контейнеров, load average > числа ядер.

## Status
Accepted

## Date
<YYYY-MM-DD>
```
