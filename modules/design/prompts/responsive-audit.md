# Адаптив-аудит — расширенный набор ширин и нестандартные сценарии

Запускай после сборки всех экранов (базовый mobile уже собран вместе с desktop), перед выкладкой или после крупных изменений UI.

Нужно на входе: экраны собраны и запускаются через `npm run dev`; `docs/screens/<url>.md` по каждому экрану.

Результат: все страницы корректны на 320 / 414 / 768 / 1024 / 1440 / 1920; нестандартные сценарии адаптации решены; узкие экраны выдерживают экстремальный контент.

Правило фикса везде: чинить в компоненте (`shared/ui/`, `widgets/`), не локальным override на странице.

## Шаг 1 — Прогон всех страниц на расширенном наборе ширин

Playwright MCP (`browser_navigate` → `browser_resize` → `browser_take_screenshot`), скриншоты в `docs/local-snapshots/`:

```
320×800   — самый узкий (iPhone SE)
414×896   — крупный телефон
768×1024  — планшет
1024×768  — маленький desktop / iPad Pro
1440×900  — desktop
1920×1080 — wide-screen
```

Без Playwright MCP — тот же Playwright скриптом через `npx playwright`, затем прочитать скриншоты.

Чек-лист на каждой ширине × странице:
- [ ] Нет горизонтального скролла
- [ ] Текст и контент не вылезают из контейнеров
- [ ] Интерактивные элементы не перекрыты sticky/fixed-элементами
- [ ] Картинки масштабируются пропорционально
- [ ] На 320 tap-таргеты ≥ 44×44
- [ ] На 1920 контент не теряется в пустоте (есть max-width или fluid scaling)

## Шаг 2 — Нестандартные сценарии

| Сценарий | Mobile-решение |
|---|---|
| Многоуровневое меню (2+ уровня) | accordion / drawer с back / sheet |
| Таблица 10+ колонок | горизонтальный скролл / карточки / приоритизация колонок |
| Сложная модалка (multi-step, длинная форма) | full-screen / bottom-sheet / wizard-экраны |
| Hover-only действия | всегда видимы / kebab-меню / swipe-actions |
| Drag-and-drop | long-press + контекстное меню / стрелки переноса |
| Графики | упрощённая версия / только summary |
| Важная информация в tooltip | перенести в видимый текст |

Экран попадает в сценарий, а базовое решение не подходит → спроси пользователя и запиши решение в `docs/screens/<url>.md` (раздел про адаптив).

## Шаг 3 — Экстремальный контент на 375px

Кейсы, которые ломаются именно на узком вьюпорте:
- неразрывные строки в тексте (URL, токен, `@username`, email в контенте) — переносятся (`overflow-wrap: break-word`);
- длинные подписи кнопок/CTA — переносятся или ужимаются, не вылезают;
- ряды чипов/тегов/фильтров — wrap или горизонтальный скролл-контейнер;
- длинные слова в заголовках — переносятся без скролла;
- большие числа и цены («1 234 567 ₽») в узких колонках — помещаются;
- счётчики и бейджи («99+») — не распирают контейнер;
- много табов / длинные хлебные крошки — scroll-tabs или свёртка;
- пары label + value — на узком в одну колонку или перенос значения;
- длинные пункты Select/dropdown — не за краем экрана, ellipsis в своей ширине;
- статус-pill с длинным текстом — перенос/ужатие, иконка не отрывается;
- toast/alert с длинным текстом и кнопкой — не наезжают, не за вьюпортом;
- строка списка (аватар + длинное имя + мета + действие) — действие доступно;
- картинки экстремальных пропорций — `object-fit` / `max-height`, без скролла;
- код-блоки — собственный горизонтальный скролл внутри блока;
- длинный placeholder/value в Input — ellipsis внутри поля;
- локализованные даты, время, единицы («29 мая 2026 г., 14:30», «−12,5 %») — помещаются;
- граничные значения (`0`, отрицательные, «—») — осмысленно, без пустот.
