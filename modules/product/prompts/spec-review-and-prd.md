# Spec Review + PRD — финальная сверка спецификации и одностраничник

Запускай, когда спецификация продукта собрана и нужно довести её до полноты и выпустить `docs/PRD.md`.

Нужно на входе: в `docs/spec.md` есть разделы «Продукт», «Платформа», индекс экранов; в `docs/screens/` лежат файлы экранов.

**Делаешь:** сверяешь `spec.md` и `docs/screens/<url>.md` с каноничной структурой; дочитываешь Figma/скриншоты на пропущенные элементы и состояния; закрываешь оставшиеся `[?]` коротким интервью; генерируешь `docs/PRD.md`.

**Не делаешь:** не описываешь продукт с нуля, не задаёшь вопросов о концепции, не строишь новые экраны.

## Роли файлов

| Файл | Для кого | Что внутри |
|---|---|---|
| `docs/spec.md` | AI и разработчик — контракт сборки, **единственный источник правды** | Продукт, платформа, модель данных, доступы, уведомления + индекс экранов (~150–400 строк) |
| `docs/screens/<url>.md` | AI и разработчик | Один экран: доступ, layout, данные, состояния, действия, связи, валидация (40–150 строк) |
| `docs/PRD.md` | Партнёры, инвесторы, новые люди, сам автор после паузы | Проекция раздела «Продукт» на одну страницу |

Синхронизация: продуктовая часть меняется сначала в `spec.md`, затем PRD.md перегенерируется.

## Порядок

1. Прочитай `docs/spec.md` и все `docs/screens/*.md`.
2. Есть Figma или скриншоты → дочитывание (ниже).
3. Сверь с каноничной структурой.
4. Пустые/отсутствующие разделы → вопросы пользователю.
5. Особо — «Действия»: у каждого кликабельного элемента должен быть результат.
6. Покажи финальный `spec.md`.
7. Сгенерируй `docs/PRD.md`.

## Дочитывание макетов

Цель: в каждом `docs/screens/<url>.md` описан каждый кликабельный элемент — кнопка, ссылка, иконка, поле, переключатель.

**Figma MCP доступен:**
1. По каждому экрану индекса — `get_design_context` (+ `get_screenshot`), выпиши все интерактивные элементы: кнопки, ссылки, иконки-кнопки, тоглы, чекбоксы, поля, табы, дропдауны, аватар-меню, контекстные меню, навигацию.
2. Элемента нет в файле → строка в «Действия»: `Клик на «<элемент>» → <результат>`. Результат понятен из макета (линк, ховер, следующий фрейм) — заполни сам; нет — `[?]` и в общий список вопросов.
3. Состояния empty / loading / error / success: нарисованы → перенеси описание; нет → «не нарисовано, нужен ответ».
4. Формы: поля и видимые правила (required, маски, подсказки) → раздел «Валидация».

**Только скриншоты** (`docs/screens/*.png` и др.): сам опиши, что видно (заголовок, блоки, интерактивные элементы), и дозаполни файлы так же. Неясное — в список вопросов.

Затем задай собранные вопросы по одному, отдельными сообщениями. Каждый ответ — сразу в файл экрана.

## Каноничная структура spec.md

```markdown
# Spec продукта <name>

## Продукт
- **Что:** [одно предложение]
- **Проблема, которую решаем:** [одно-два предложения]
- **Ключевая ценность:** [почему выбирают этот продукт]
- **Для кого:** [роли: один тип / админ+пользователь / гость+авторизованный / B2B]
- **Главная задача:** [главный сценарий за один проход]
- **Что НЕ делаем в первой версии (out of scope):** [список]

## Платформа
- **Основная:** web (responsive) — адаптируется под мобильный браузер

## Данные (модель)

### User
- id: uuid
- email: string (уникальный)
- name: string
- role: 'user' | 'admin'
- createdAt: timestamp

### [Сущность 2]
...

## Экраны (индекс)
- [/<url> — <Название>](screens/<url>.md) — назначение одной строкой

## Доступы и роли

| Роль | Что видит |
|---|---|
| user | свои данные, основной флоу |
| admin | всё + админка |
| гость | главная, login, signup |

## Уведомления

| Триггер | Канал | Получатель | Текст / шаблон |
|---|---|---|---|
| Регистрация | Email | пользователь | «Добро пожаловать, {{name}}» |
```

## Каноничная структура файла экрана — `docs/screens/<url>.md`

```markdown
# /<url> — <Название>

**Доступ:** [все / только залогиненные / роль]
**Источник:** [Figma node-id / `docs/screens/<file>.png` / текстовое описание]
**Layout:** контейнер (max-width), padding, внутренний gap, поведение на ≤640px / 768px
**Данные:** [API endpoint, сессия, props]
**Состояния:** default / loading / empty / error / success — что в каждом
**Действия:**
- Клик на [элемент] → [куда ведёт / что делает]
- Submit формы [имя] → POST [endpoint] → success / error
**Связи с другими экранами:** откуда сюда / куда отсюда
**Валидация (если есть формы):** поле — правило — сообщение об ошибке
```

## Чек-лист

Скажи пользователю, что есть и чего нет:

- [ ] «Продукт» заполнен (что / для кого / задача)
- [ ] «Платформа» указана
- [ ] «Данные»: есть User и основные бизнес-сущности
- [ ] Каждый экран — в своём `docs/screens/<url>.md`, в `spec.md` индекс со ссылками
- [ ] В каждом файле экрана: Доступ, Источник, Layout, Данные, Состояния (минимум default + loading + empty + error), Действия
- [ ] В «Действиях» нет пустых строк и «TBD» — у каждого элемента конкретный результат
- [ ] У каждого экрана есть хотя бы один путь входа и один путь выхода — нет тупиков и orphan-экранов
- [ ] «Доступы и роли» заполнены
- [ ] «Уведомления» — если в продукте есть email / Telegram / in-app

По каждому пустому пункту — один вопрос, не списком.

**Пробел в «Действиях»** — называй конкретный экран и элемент и выбери форму:
1. Предложи: «Предлагаю так: [сценарий]. Подходит?»
2. Уточни: «Кнопка "[название]" на экране "[экран]" — [А] или [Б]?»
3. Запроси материал: «Покажи этот экран в Figma или опиши словами, что должно произойти».

После сверки покажи финальный `spec.md` целиком.

## Генерация PRD.md

Поля бери **только** из раздела «Продукт» в `spec.md`, новых вопросов не задавай.

```markdown
# PRD — <название продукта>

> Описание продукта на одну страницу. Источник правды — `docs/spec.md`; изменения продуктовой части — сначала туда, затем перегенерация этого файла.

## Что за продукт
<spec.md «Продукт → Что»>

## Какую проблему решает
<«Продукт → Проблема»>

## Ключевая ценность
<«Продукт → Ключевая ценность»>

## Для кого
<«Продукт → Для кого»>

## Главный пользовательский сценарий
<«Продукт → Главная задача»>

## Основные действия в продукте
<«Продукт → Основной функционал» — крупными блоками, без UI-деталей>

## Платформа
<«Платформа»>

## Что НЕ делаем в первой версии (out of scope)
<«Продукт → Out of scope»>

## Где детали
- Технический контракт (экраны, состояния, данные): [`spec.md`](spec.md)
- Дизайн-система: [`DESIGN.md`](DESIGN.md) — если есть
- История решений: `docs/memory/decisions/` — если есть
```

Правила PRD:
- PRD — проекция `spec.md`, не источник новой информации.
- Без технических деталей (БД, API, состояния экранов).
- Поле в `spec.md` пустое → в PRD плейсхолдер `<заполни в spec.md>`, не выдумывай.
- Ссылки «Где детали» на несуществующие файлы не ставь.

## Память

Если есть `docs/memory/state.md` — допиши:

```markdown
## Спецификация продукта — завершено
- spec.md сверен: <date>
- PRD.md сгенерирован: <date>
- Путь детализации: <A — Figma / Б — скриншоты / В — без дизайна>
```
