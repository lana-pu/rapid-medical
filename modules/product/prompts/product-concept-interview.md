# Product Concept Interview — что за продукт и для кого

Запускай в начале нового проекта. AI проведёт интервью и заполнит в `docs/spec.md` разделы «Продукт» и «Платформа» плюс edge cases уровня продукта.

**Не делаешь здесь:** скелет экранов, детализацию экранов, модель данных, layout. Это следующий слой — `screens-spec-from-figma.md` (есть Figma) или `screens-spec-from-sketches-or-idea.md` (скриншоты или только идея).

## Принципы интервью

- **Один вопрос — одно сообщение.** Спросил → дождался ответа → следующий.
- **Формулировка вопроса — твоя**, разговорным тоном; текст этого промта в чат не копируй.
- **Размытый ответ** → предложи 2–3 варианта на выбор; дальше не иди, пока ответ не станет понятным.
- **Неполный, но валидный ответ** → принимай, недостающее заполняй разумным default.
- **Ты собираешь спеку, а не консультируешь.** Выбор пользователя не оспаривай, охват сузить не предлагай. «Для всех» — валидный ответ.
- **Сначала материалы, потом вопросы.** Что видно в Figma/скриншотах или уже сказано — бери оттуда; спрашивай только пробелы.
- **UX-полнота.** Пользователь называет кнопку/экран → сразу уточни, что она делает, куда ведёт, что показывает после. Состояния (нет данных / ошибка / загрузка) — часть спеки.

## 0. Подготовка

Создай `docs/spec.md` (если нет) по структуре в конце промта.

## 1. Состояние идеи

Спроси, в каком состоянии идея, варианты:
- готовая — готов рассказать;
- расплывчатая — нужна помощь додумать;
- идеи нет — подобрать вместе.

## 2. Какие материалы есть

Отдельным сообщением, варианты:
- Figma с экранами/прототипами (попроси ссылку);
- скриншоты / наброски (попроси загрузить);
- только в голове / расскажет голосом;
- ничего — придумываем с нуля.

Запиши в `## Продукт` строку `*Исходные материалы: <вариант>*`.

**Если дали ссылку на Figma — только поверхностный скан:**
1. Проверь, что Figma MCP доступен (`get_metadata` на ссылку). Если инструментов Figma нет — подключи по разделу «Подключение Figma MCP» из `screens-spec-from-figma.md`, затем вернись сюда.
2. Вызови **только** `get_metadata` на корень файла → карта страниц и фреймов. `get_design_context` по экранам здесь не вызывай.
3. Одним сообщением: «нашёл `<N>` страниц и `<M>` экранов — `<реальные имена из get_metadata>`», детальный разбор будет на этапе экранов; сейчас — вопросы о сути продукта (Figma показывает как выглядит, а не что это и для кого). Типовые `/login`, `/signup` не подставляй.
4. Размер файла не комментируй и сократить не предлагай.

**Если скриншоты** — подтверди «вижу N скриншотов», не описывай их сейчас.

Развилка: идея готова → шаг 4; расплывчатая или нет → шаг 3.

## 3. Подобрать конкретный продукт

- **Расплывчатая идея:** одним сообщением 2–3 конкретных продукта в его области, по строке о механике. Попроси выбрать или предложить свой.
- **Идеи нет:** одним сообщением несколько типовых вариантов (название + строка о механике), например: трекер привычек; планировщик задач; отчёты/метрики/дашборды; квизы, тесты, опросы; парсер вакансий*; контент-студия*; личный дайджест новостей*; обучающая платформа (короткие занятия + прогресс + проверка)*; браузерные игры с аккаунтами и таблицей рекордов. `*` — нужны платные AI-токены (например, через OpenRouter).
- Не подошло — один уточняющий вопрос про интересы/личные задачи и ещё 2–3 варианта.

## 4. Раздел «Продукт» (адаптивно)

Это поля, а не обязательный список вопросов. Ясно из контекста → сформулируй сам, подтверди одной репликой («зафиксировал»), запиши в spec.md. Неясно → один вопрос.

1. **Что за продукт** — одно предложение. Обязательно. Слишком абстрактно («приложение для здоровья») → один раз попроси конкретики.
2. **Для кого (роли)** — один тип / админ + пользователи / гость + авторизованный / B2B-иерархия. Про роли и права, не про маркетинг. Есть админка в материалах → роль админа уже понятна.
3. **Главная задача** — основной сценарий за один проход. Обычно выводится из полей 1 и 4.
4. **Основной функционал (flow)** — крупные блоки. Длинный список принимай целиком.
5. **Платформа** — по умолчанию web (responsive), адаптация под мобильный браузер. Отдельно не спрашивай; меняй, только если материалы явно указывают иное (например, iOS-приложение).
6. **Проблема и ценность** — опционально. Продукт «для себя» или боли нет → оставь пустым, не выдумывай.
7. **Out of scope** — опционально. Само не всплыло → не вытягивай.

## 5. Edge cases (3–5 тем, каждая отдельным сообщением)

Выбери релевантные главному сценарию:
- empty state главного экрана (пользователь ещё ничего не создал);
- loading при долгих операциях;
- error при ошибке загрузки / сети;
- незавершённые действия — теряются или черновик;
- роли с разными правами (просмотр vs полный доступ);
- одновременная работа двух пользователей с одним объектом;
- уведомления — нужны ли и каким каналом (email / Telegram / in-app);
- доступ к закрытому экрану без прав (редирект / 403 / сообщение).

Добавь 1–2 вопроса специфичных для продукта (например, для трекера привычек: можно ли отметить задним числом, рвётся ли серия при пропуске дня). Ответы — в spec.md: блок `### Edge cases` внутри «Продукт»; про каналы уведомлений — в «Уведомления».

## Структура spec.md

```markdown
# Spec продукта <name>

## Продукт
- **Что:** [одно предложение]
- **Для кого:** [роли в системе]
- **Главная задача:** [основной сценарий за один проход]
- **Основной функционал:** [основные фичи]
- **Проблема, которую решаем:** [опционально]
- **Ключевая ценность:** [опционально]
- **Что НЕ делаем в первой версии (out of scope):** [опционально]

### Edge cases
- [тема — решение]

## Платформа
- **Основная:** web (responsive) — адаптируется под мобильный браузер

## Экраны (индекс)
*[заполняется на этапе экранов]*

## Данные (модель)
*[заполняется на этапе экранов]*

## Доступы и роли
*[заполняется на этапе экранов]*

## Уведомления
*[из edge cases, если всплыло]*
```

## Финал

Покажи разделы «Продукт» и «Платформа», короткую сводку «что собрали», и допиши в конец «Продукт»:
`*Путь детализации: <A — Figma / Б — скриншоты / В — без дизайна>*`
