# Screens Spec from Sketches or Idea — скелет и детализация экранов без Figma

Запускай, когда нужно расписать экраны продукта, а Figma с MCP-доступом нет: есть скриншоты/наброски/дизайн в другом инструменте (режим Б) или только идея (режим В).

Нужно на входе: `docs/spec.md` с заполненными разделами «Продукт» и «Платформа» (если нет — сначала `product-concept-interview.md`).

**Делаешь:**
1. Скелет состава продукта: Б — по скриншотам, В — типовой набор под продукт; группировка по разделам и согласование → `spec.md → ## Экраны (индекс)`.
2. Файл на каждый согласованный экран: `docs/screens/<url>.md` (доступ, layout, данные, состояния, действия, связи, валидация).
3. Разделы `spec.md`: «Данные (модель)», «Доступы и роли», «Уведомления».

**Не делаешь:** не спрашиваешь «что за продукт / для кого / какая проблема / главный сценарий» — это уже в `spec.md → Продукт`. Маркетинговый лендинг здесь не детализируешь — он делается отдельным промтом модуля design.

## 0. Режим

Спроси:
> Б. Есть скриншоты/картинки экранов — пришлю
> В. Дизайна нет, только идея — придумываем с нуля

Шаги Б1–Б2 или В1–В2 отличаются, с шага 3 — общие.

---

## Режим Б — скриншоты

### Б1. Картинки

Попроси прислать все скриншоты (в чат или в `docs/screens/`) и к каждому одну строку сути экрана. Проверь, что картинки доступны и подписаны; URL экрана придумай сам. Непонятно — спроси конкретно: что показывает экран, куда с него перейти, что делает эта кнопка.

### Б2. Карта экранов

Для каждой картинки запиши в `docs/screens-map.md` только то, что реально видно:

```markdown
## Экран: <название> (`<url>`)
- **Источник:** `docs/screens/<filename>.png`
- **Что вижу:**
  - Заголовок / текст
  - Блоки по порядку
  - Кнопки / ссылки / формы / списки
  - Какие данные показываются
- **Что НЕ видно (но возможно есть):**
  - Состояния (loading/empty/error)
  - Что при клике на X, Y, Z
```

### Б2.5. Согласование скелета

Сгруппируй экраны: **Публичная часть** (главная, регистрация, вход, восстановление, публичные страницы) / **Личный кабинет** (основной флоу, профиль, настройки, история) / **Админка** (если есть роль админа) / **Прочие**.

Про себя назови 1–3 аналога продукта этого типа. Покажи один список по разделам (на экран строка: `URL — Название (что показывает)`) и одним сообщением спроси:

> 1. Все ли экраны нужны в первой версии? Что исключаем?
> 2. Каких экранов не хватает? (восстановление пароля, профиль, настройки уведомлений, 404/403, онбординг, экраны под «Основной функционал» из spec.md)
> 3. У аналогов ({1–3}) на ключевых экранах обычно есть {2–4 предложения: фильтры/сортировка/поиск, пагинация, массовые действия, избранное, экспорт, empty/loading}. Что добавляем? (да / нет / позже)
> 4. Группировка корректна?

По ответу в `screens-map.md`: исключённые → `*[не делаем в первой версии]*`; недостающие → `*[экран нужен, но не нарисован — описываем словами]*`; принятые усиления → в индекс или в описание экрана; отклонённые → `*[не делаем в первой версии]*`; группировку правь.

Запиши индекс в `spec.md` (формат — в разделе «Индекс экранов» ниже). Дальше — шаг 3.

---

## Режим В — без дизайна

### В1. Скелет (предлагаем + согласовываем)

Подбери типовой набор под `spec.md → Продукт` и платформу, сгруппируй и предложи:

```
Публичная часть: главная (лендинг или список), регистрация, вход, восстановление пароля
Личный кабинет: главный экран (основной сценарий), профиль, настройки, история (если есть аудит)
Админка (если есть роль админа): список пользователей, детали пользователя, управление контентом
Прочие: онбординг, публичный каталог, 404/403 — если нужны
```

Спроси: какие нужны, какие ещё под «Основной функционал», что не делаем в первой версии. Добавь: «у аналогов ({1–3}) на ключевых экранах обычно есть {2–4 предложения} — что добавляем? (да / нет / позже)».

Принятое фиксируй в `screens-map.md`, отклонённое — `*[не делаем в первой версии]*`. Не может решить по экрану → 2–3 варианта (пример: «Настройки уведомлений — А: один общий переключатель, Б: по каждому событию, В: не делаем в первой версии»). Уточняй до полного списка ~5–15 экранов.

`docs/screens-map.md`:

```markdown
## Скелет состава продукта

### Публичная часть
| URL | Название | Доступ | Что показывает |
|---|---|---|---|
| `/` | Главная | все | ... |
| `/login` | Вход | неавторизованные | форма |

### Личный кабинет
| URL | Название | Доступ | Что показывает |
|---|---|---|---|
| `/dashboard` | Главный экран | авторизованные | ... |
```

Параллельно — индекс в `spec.md` (формат ниже).

### В2. Описание каждого экрана

По каждому экрану три вопроса, по одному:
1. Что на экране — заголовок, основные блоки?
2. Какие действия — что можно нажать/заполнить?
3. Куда переходим / что меняется после действия?

После каждого ответа дописывай в `screens-map.md`:

```markdown
### /<url> — <название>
- Что на экране: ...
- Действия: ...
- Переходы / изменения: ...
```

---

## Индекс экранов (формат для spec.md)

```markdown
## Экраны (индекс)

### Публичная часть
- [`/login` — Вход](screens/login.md)

### Личный кабинет
- [`/dashboard` — Главный экран](screens/dashboard.md)
```

## 3. Пробелы логики (общий)

Для каждого экрана из карты запиши в `docs/logic-gaps.md` всё неопределённое — даже «очевидное».

Чек-лист:
1. **Кнопки и ссылки** — куда ведут, что при клике, активны ли во всех состояниях.
2. **Формы** — поля, валидация, submit, ошибка, успех.
3. **Попапы, модалки, подтверждения** — заголовок, кнопки, что при «Да» / «Нет» / крестике.
4. **Тосты и уведомления** — событие, текст, длительность, крестик.
5. **Списки и таблицы** — empty (текст + CTA), loading, error.
6. **Откуда данные** — БД / API / сессия / пропсы; что если не пришли.
7. **Доступы** — кто видит; не тот пользователь → редирект или ошибка.
8. **Навигация** — откуда сюда, куда отсюда.

```markdown
## Экран: <название>
### Действия
- [ ] Клик на "[кнопка]" → ?
### Модалки / попапы
- [ ] Попап "[название]" — кнопки? после подтверждения? после отмены?
### Состояния
- [ ] Пустое состояние — текст и CTA?
- [ ] Ошибка загрузки — что показываем?
### Данные
- [ ] Откуда берётся [поле]?
### Доступы
- [ ] Кто видит? Что если нет прав?
```

## 4. Закрыть пробелы — по одному вопросу

Сводка `logic-gaps.md` одним сообщением (обзор), затем каждый пробел отдельным сообщением, жди ответа. Неполный ответ → разумный default.

После ответа:
1. Логику экрана (состояния, действия, связи, валидация) — в `docs/screens/<url>.md`; общее (данные, доступы, уведомления) — в `spec.md`.
2. `[x]` у закрытых пунктов `logic-gaps.md`.
3. «Не знаю» не принимай — предложи в ответе: «А. … Б. … В. … или своё».
4. Экран прояснился → «Представляю экран так: […]. Похоже?»

Пока в `logic-gaps.md` есть `[ ]` — к шагу 5 не переходи.

### Верификация

1. На **каждый** экран из `screens-map.md` (кроме исключённых) есть `docs/screens/<url>.md`. Нет — создай сейчас из карты и `spec.md`.
2. В «Действиях» нет строк без результата.
3. У каждой модалки перечислены кнопки и их результат.
4. У каждого экрана с данными есть empty, loading, error.

Нашлось — вопрос именно по этому элементу. Затем: «Проверил — [N] экранов, каждое действие закрыто. Переходим к модели данных?»

## 5. Модель данных

Сущности из ответов («список заказов» → Order) → `spec.md`:

```markdown
## Данные (модель)

### User
- id, email, name, role, createdAt

### <Сущность 2>
...
```

## 6. Сборка spec.md

```markdown
# Spec продукта <name>

## Продукт
## Платформа
## Данные (модель)
## Экраны (индекс)   ← только ссылки на docs/screens/<url>.md
## Доступы и роли    ← таблица «Роль | Что видит»
## Уведомления       ← таблица «Триггер | Канал | Получатель | Текст»
```

Файл экрана `docs/screens/<url>.md`:

```markdown
# /<url> — <Название>

**Доступ:** [все / залогиненные / роль]
**Источник:** [`docs/screens/<file>.png` / текстовое описание]
**Layout:** контейнер (max-width), padding, gap, поведение на ≤640px / 768px
**Данные:** [API endpoint, сессия, props]
**Состояния:** default / loading / empty / error / success — что в каждом
**Действия:**
- Клик на [элемент] → [куда / что делает]
- Submit формы [имя] → POST [endpoint] → success / error
**Связи с другими экранами:** откуда сюда / куда отсюда
**Валидация:** поле — правило — сообщение об ошибке
```

## 7. Результат

1. `spec.md` целиком.
2. `screens-map.md` и `logic-gaps.md`.
3. `tree docs/screens/` + подтверждение: число экранов в карте = число файлов. Не сходится — создай недостающие.

## Визуал — не здесь

Спека описывает, что строим; как выглядит — `docs/DESIGN.md` (модуль design). Правило для всех последующих изменений: DESIGN.md → UI-кит → экраны. Если в режиме В нет визуальных предпочтений — попроси назвать продукт-референс по стилю (Linear, Notion, Stripe, Apple, Discord…) и запиши в `spec.md → Платформа` строкой `*Референс стиля: …*`.

## Правила

- **Не додумывай.** Б — только то, что на картинке; В — только то, что сказал пользователь.
- **По одному вопросу**, никогда списком.
- **Заполняй spec.md и файлы экранов по ходу.**
- **В режиме Б сохраняй картинки** в `docs/screens/` — нужны при сборке UI.
